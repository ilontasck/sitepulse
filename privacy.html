5. Website audits submitted by you

When you submit a URL for a website audit, the following data is processed:

  • The submitted URL — normalised (scheme enforced as https://, hash fragment and credentials stripped), then stored in the database linked to your account.
  • DNS resolution of the URL hostname — performed server-side before the audit begins, to verify the target is a public host. No result is stored permanently.
  • HTTP fetch of the target website — the server sends a request to the URL you submitted, identifying itself with the User-Agent string SitePulseAuditBot/0.2 (+https://sitepulse.local). Up to three HTTP redirects are followed if the server returns them. The HTML content of the page is read (up to 1.5 MB) to perform analysis.
  • Optional rendered audit — when this feature is enabled, the server launches a local Chromium browser to visit the URL and run a Lighthouse performance analysis. All browser network requests are subject to the same SSRF safety restrictions as the initial fetch.

The content of the websites you submit is processed only for the purpose of producing the audit report. The HTML of audited pages is not stored — only the derived audit scores and findings are retained.

URL safety

The service enforces strict protections against server-side request forgery (SSRF): only public HTTP/HTTPS URLs with globally routable IP addresses are accepted. All private IP ranges (RFC 1918, link- local, loopback) and internal hostnames are blocked at both the initial submission stage and during audit execution.

Legal basis

Processing the submitted URL and performing the audit is necessary for the performance of the service you requested.

6. Stored audit reports

Completed audit reports are stored in the database associated with your account. Each stored report contains:

  • The normalised URL and domain of the audited website
  • An overall quality score and per-category scores
  • Pass/fail results for each individual check with descriptive text
  • Technical findings from the audited site's HTTP response headers
  • Response time, HTML byte size, and HTTP status code of the target
  • If rendered auditing was performed: Core Web Vitals (LCP, CLS, FCP, Speed Index, TBT), Lighthouse category scores, browser console error counts, and DOM size metrics
  • Scanner metadata: mode, adapters used, timestamp, and any warnings

The audit report is not designed to contain NOQORI account credentials or account profile data. It may contain technical information obtained from the submitted public website, including URL-related data, HTTP response information, checks and rendered diagnostics.

Reports are linked to your account by your user ID and are accessible only to you. The service enforces ownership checks on every report retrieval request.

7. Operational logs

The application writes structured telemetry to the server's standard output (process log) for operational purposes. These log entries record audit lifecycle events such as completion, failure, duration, and scanner mode. They do not contain email addresses, user IDs, or any other personal data.

The in-process rate limiter uses the requesting IP address to enforce per-client request limits. This address is held in memory only for the duration of the current rate-limit window and is never written to the database or any log file.

There is no HTTP access log. The application does not log request paths, User-Agent strings, or IP addresses to persistent storage.
